# 02 — 실패 재현과 원인 분석 (왜 "보고도 못 읽는가")

조사일: 2026-10-02 · 판독자: 세션 모델 GLM-5.3-Flash 자신(비전 실측) · 증거: `captures/`

사용자가 보고한 두 실패를 실험 리그로 재현했고, 두 개의 서로 다른 원인 + 하나의 모델 외부 구조
문제로 분해된다. **세 전부 모델에 이미지가 도달하기 전에 발생한다** — 이것이 이 연구의 핵심 판정이다.

## 실험 1 — 전체 화면 기본 경로 (GDI 캡처 → 1280px 축소 → 모델 판독)

파일: `captures/r2-baseline-fullscreen.png`(2560×1600) → `r2-baseline-1280.png`(74.9KB, 축소 222ms)

1280px 이미지를 내 비전으로 읽은 결과:

| 항목 | 결과 |
|---|---|
| ZCode 세션 패널 텍스트(중형) | 판독 ✓ |
| **ALPHA-4217**(대형, 테두리 없는 폼) | 판독 ✓ — 그러나 **소속 앱 판별 근거 없음** |
| 폼의 2번째 줄(10pt: `K7X-291 PLUME-OBSERVER 미세문자-8846`) | 부분 판독(흐릿) |
| 폼의 3번째 줄(9pt 한국어) | **판독 실패**(수 px로 붕괴) |
| 메모장 상태표시줄("120자", "UTF-8") | 판독 ✓ |
| **메모장 본문 4줄** | **완전히 보이지 않음 — 빈 영역** |

### 발견 A — 가림(occlusion)은 "조용한" 실패를 만든다

좌표 대조: 메모장 본문 시작 영역(화면 [555,259]+콘텐츠 오프셋)이 테두리 없는 폼 bounds
[520,300,760,440]에 겹친다. 즉 본문은 **화면에서도 가려져 있었고**, GDI 합성 캡처에는 그
영역이 앞쪽 창 픽셀로 채워졌다. 모델 입장에서는:

- 창 테두리·탭·상태표시줄은 멀쩡히 보인다("앱이 화면에 유일하게 표시되고 있다"는 관찰과 일치)
- 본문만 비어 있다
- **캡처가 손실됐다는 메타정보는 어디에도 없다** → 모델은 "본문이 비어 있다"고 보고하거나,
  더 나쁘게는 빈 영역을 근거로 추론을 계속한다

이것이 사용자 보고 ② "화면에 유일하게 표시된 앱인데도 정보를 추출하지 못한다"의 재현이다.
원인은 비전 능력이 아니라 **입력 픽셀 자체에 내용이 없는 것** — 모델 이전 단계의 손실이다.
(전체 화면 캡처에서만 생기는 문제. 창 단위 캡처는 발견 B에서 보이듯 가림을 관통한다.)

### 발견 B — 해상도 붕괴선 (텍스트 픽셀 높이 법칙)

같은 창 캡처(1586×833)를 폭별로 축소해 판독 비교(`r2-readability-ladder.png`):

| 폭 | 본문 텍스트 높이(≈) | 판독 |
|---|---|---|
| 1586(네이티브) | ~16px | ✓ 선명 |
| 1280 | ~13px | ✓ |
| 800 | ~8px | ✓ (약간 물러짐) |
| 640 | ~6.5px | **한계** — 한글 자형 붕괴, 토큰 오판 위험 |

2560 전체 화면 → 1280 축소에서는 9–10pt 텍스트가 5–6px로 떨어져 위 표의 "한계" 이하가 된다.
**경험칙: emit되는 이미지 안의 텍스트 높이 ≥ 8px(권장 ≥10px).** 이를 만족시키는 방법은
"더 크게 찍는 것"이 아니라 "더 작은 영역을 잘라내는 것"이다(03 문서 M3).

### 발견 C — 귀속(provenance)은 픽셀에 없다

테두리 없는 폼의 ALPHA-4217 패널: 픽셀만으로는 소속 앱을 알 수 없다(제목줄·테두리·태스크바
단서 전무). 이것이 사용자 보고 ①의 재현. 비전 모델은 "어딘가의 어두운 패널에 큰 텍스트"까지만
말할 수 있고, pid/앱 이름은 원리적으로 추측할 수 없다. 귀속은 픽셀 밖 정보(핸들 열거)에서 와야 한다.

## 인코더 영향 (JPEG vs PNG)

같은 텍스트 영역을 JPEG Q80 / PNG로 인코딩 후 2배 확대 비교(`r2-readability-ladder.png` C행):
**판독력 차이를 구분할 수 없었다.** JPEG Q80이 2–3배 빠름(82ms vs 222ms)을 감안하면 기본
JPEG가 옳다. 단 소형 텍스트 대량 판독·확대 검증용 크롭은 PNG 잔상 이점이 있으므로 크롭은 PNG 유지.

## 모델·계층 요인 (이번 세션에서 추가 확인한 것)

1. **GLM-5.3(비전 ✗)**: 이미지 경로는 원점에서 무효. 이 모델에서 "스크린샷 분석"은 곧
   도구 텍스트(UIA 값, 창 제목, 파일 내용) 경로여야 한다 — 시각 경로를 쓰게 하는 워크플로우 자체가 오답.
2. **셀당 래스터 1장 규칙** (이전 프로젝트에서 실측): 한 셀에서 이미지 2장을 emit하면 두 번째는
   통째로 삭제된다. 전/후 비교를 한 셀에서 하려다 정보가 사라지는 사고가 반복될 수 있다.
3. **컨텍스트 오염** (이전 프로젝트 실측): 대형 UIA 트리/이미지 혼재 컨텍스트는 이후 턴 전체의
   추론 품질을 떨어뜨린다. "더 많이 보여주기"는 정확도의 적 — **의도로 필터링한 최소 근거**만이 답이다.

## 원인 종합 — 사용자 가설에 대한 판정

| 사용자 가설 | 판정 |
|---|---|
| 도구가 건네는 이미지 데이터가 다른 LLM보다 적거나 의미 없다 | **부분 맞음** — 단 데이터량이 아니라 (a)가림 손실 (b)축소 붕괴 (c)근거 메타데이터 부재가 본체. 같은 이미지라도 창 단위 캡처+메타데이터로 GLM-5.3-Flash가 완판했다(03 문서) |
| 캡처 전에 추출 대상을 정해 제어하면 도움 된다 | **맞음** — UIA 좌표 선행 조회로 크롭 정확도가 극적으로 올라감(03 M2/M3) |
| 핸들→좌표→캡처→크롭 순서가 낫다 | **맞음** — 실측 201ms에 "전체화면에서 실패하던 판독"이 성공으로 바뀜 |
| 디버그 기능(직접 캡처)을 먼저 쓰면 Computer Use가 불필요할 수 있다 | **맞음** — UIA 값 추출은 이미지 0장·~40ms. 텍스트·값 확인 과제의 대부분을 대체한다 |

## 실패 모드 요약 (스킬이 방어해야 할 것)

| # | 실패 모드 | 증상 | 방어 |
|---|---|---|---|
| F1 | 가림 손실 | 전체화면 캡처에서 내용 영역이 빈 상태로 모델에 도달 | 창 단위 검증 캡처(가림 관통) + blank 감지 |
| F2 | 해상도 붕괴 | 8px 미만 텍스트 판독 실패 | UIA rect 크롭·확대, 폭 하한 800px |
| F3 | 귀속 불능 | 테두리 없는 영역의 소유자를 모름 | digest/리본 메타데이터 주입(픽셀 추측 금지) |
| F4 | 래스터 삭제 | 셀당 2번째 이미지가 사라짐 | 셀당 1장 가드 |
| F5 | 컨텍스트 오염 | 트리/이미지 홍수로 이후 추론 약화 | 의도 선언 → 필터링된 최소 근거만 |
| F6 | 비전 없는 세션 | GLM-5.3에서 이미지가 토큰 낭비 | 비전 게이트 → 도구 전용 경로 |
